# M-A gate: `cram_codec::container`

Measured on `mew` (Intel i9-12900K, x86_64, Linux), release build, single thread,
2026-10-21. Raw per-arm numbers: [`ma-gate.csv`](ma-gate.csv) (every arm alone,
then the container, `cram bench`). Table generated by [`gate.py`](gate.py).

Reproduce: `cargo build --release -p cram-codec --bin cram`, then
`cram bench FILE [--hint f32:64x128x128[:psnr=60]]` per file.

Corpus: the 12 Silesia files; `cargo-metadata.json` (3.5 MB, `cargo metadata`
of the tang workspace); `journal.log` (34.5 MB, `journalctl -n 300000` on mew);
`silesia.zip` (already compressed); the five 64×128×128 f32 fields in
`~/cram-site-in` — once with no bound (lossless) and once with `psnr=60`
(lossy arm enabled).

Header = `CRM1` + method byte + varint length + CRC-32 = 13 bytes for all
these sizes. "tie" means cram = best arm + header exactly (it picked that arm).

## Verdict

**Passes on 24 of 25 files, and only ties: everywhere cram equals best arm + 13 header bytes.**
It never beats the best single arm, because the container just picks one arm.

**`silesia.zip` misses the gate when measured against all arms.** The sniff spots the
ZIP magic, so cram runs only stored + zstd-3 and writes 68,100,746 bytes. xz-9 alone
gives 67,957,132, which is 143,614 bytes (0.21%) smaller. Measured against the arms the
policy actually enables (stored and zstd-3, best 68,100,733), cram passes with +13.
That miss is the price of the sniff: it costs 0.2% here but cuts encode time to
490 MB/s, where running every arm would hold it near the slowest arm, brotli at 0.89 MB/s.

Encode speed is low on purpose. `compress` runs every enabled arm, so its time is the
sum of all the arms (xz-9, zstd-19 and brotli-11 together give 0.4–1 MB/s). Decode
speed is the speed of whichever arm was picked.
